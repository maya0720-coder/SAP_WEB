# G-SAP Webservice 통합 기획서 v0.4

Nov 16, 2026 · @maya0720 · Golfzon IE팀

## 1. Executive Summary

**결론:** 3개 대상(외부 영업, 결재자, 배송기사·SCM)을 하나의 외부
웹서비스로 묶어 제공합니다. SAP는 인터넷에 직접 노출하지 않고, 이미 운영
중인 BSG AWS EAI를 유일한 통로로 둡니다. 1차 오픈 범위는 **발주서
등록·결재함**으로 제한하고, **배송 위치 조회는 위치정보법 검토 후
2차**로 진행하기를 권고합니다.

| 구분     | 권고안                                                              | 이유                                                                   |
|----------|---------------------------------------------------------------------|------------------------------------------------------------------------|
| 1차 범위 | 가맹 발주서 등록·임시저장, 결재함(발주서·판매가·매입단가 승인/반려) | SAP 화면이 이미 있어 RFC 재사용률이 높고, 업무 지연 효과가 즉시 나타남 |
| 2차 범위 | 배송 진행 상태 조회, 기사 위치(이벤트 기반)                         | 개인위치정보 동의·사업 신고 여부 등 법무 검토가 선행되어야 함          |
| 인증     | fs.golfzon.com(Entra ID 연동) SSO 단일화 + 조건부 접근(MFA)         | 별도 계정 발급 없음, 퇴사자 즉시 차단                                  |
| 권한     | SAP 역할(AGR_USERS) 기준으로 화면 노출, 실행 시 SAP 측 권한 재확인  | 웹 권한과 SAP 권한의 불일치 방지                                       |
| 연동     | Web(BFF) → EAI → SAP RFC, 웹서버에는 SAP 자격증명 없음              | 공격 표면 최소화, 기존 EAI 보안 통제 재사용                            |

**의사결정 요청 (3건)**

1.  EAI 경유 구조 승인 및 EAI 인증 방식 상향(API Key 단독 → mTLS 또는
    OAuth2 Client Credentials + IP 허용목록)

2.  Entra ID 조건부 접근 정책(MFA, 세션 재인증 주기) 적용 승인 —
    IT보안팀

3.  배송기사 위치 수집 방식 결정(권고: 실시간 추적이 아닌
    '출발·도착·완료' 이벤트 시점 수집) 및 법무 검토 착수

## 2. Agenda Framing · MECE 질문 구조

**핵심 질문(Agenda):** "SAP 내부에만 있는 입력·승인·조회 업무를, 보안
수준을 낮추지 않고 외부(모바일·태블릿)에서 처리하게 할 수 있는가?"

| MECE 축             | 하위 질문                                           | 가설                                                                              | 검증 방법                                                             |
|---------------------|-----------------------------------------------------|-----------------------------------------------------------------------------------|-----------------------------------------------------------------------|
| ① 업무 가치         | 외부 입력·결재가 실제로 지연·오류를 줄이는가?       | H1. 현장 입력으로 재입력 오류가 줄고, 외부 결재로 승인 리드타임이 줄어든다        | 현행 요청일→승인일 차이(단가변경 승인 화면의 요청일 컬럼) 기준선 측정 |
| ② 사용자·접근       | 누가, 어떤 기기로, 어떤 화면에 접근하는가?          | H2. 기존 SAP 역할만으로 웹 메뉴를 통제할 수 있다                                  | 대상자별 SAP 역할·T-CODE 매핑 샘플 추출                               |
| ③ 데이터 연동       | SAP와 어떻게, 어느 통로로 통신하는가?               | H3. 기존 EAI를 재사용하면 신규 네트워크 개방 없이 연동 가능하다                   | EAI 사업자와 신규 인터페이스 PoC 1건                                  |
| ④ 보안·컴플라이언스 | 외부 노출에 따른 위험을 통제할 수 있는가?           | H4. SSO+MFA+WAF+EAI 격리로 VPN 수준 이상의 통제가 가능하다                        | 6장 Evidence Matrix                                                   |
| ⑤ 위치·개인정보     | 배송기사 위치를 합법적·기술적으로 수집할 수 있는가? | H5. 웹만으로는 상시 추적이 어렵고, 이벤트 기반 수집이 법·기술 양면에서 현실적이다 | 7장 방법론 비교, 법무 검토                                            |

- 사실/추론 구분: 위 가설은 모두 **미검증 가설**입니다. H1의 효과 수치는
  아직 측정하지 않았으므로 본 문서에 기재하지 않았습니다.

## 3. 서비스 기획서

서비스명은 **G-SAP Webservice**(v0.2 명칭 유지)입니다. 하나의 .com
도메인에서 역할에 따라 서로 다른 메뉴를 보여줍니다.

### 3.1 대상별 AS-IS → TO-BE

| 대상                   | AS-IS (문제)                                                                     | TO-BE (제공 기능)                                                         | 기대 효과                             |
|------------------------|----------------------------------------------------------------------------------|---------------------------------------------------------------------------|---------------------------------------|
| 외부 영업사원·영업지원 | 현장에서 엑셀·메모 기록 → 귀사 후 VPN+SAP GUI 재입력. 기억 오류로 인한 기재 오류 | 태블릿·모바일에서 가맹 발주서 작성·임시저장·등록, 내 발주서 진행상태 조회 | 이중 입력 제거, 현장 데이터 원본 보존 |
| 결재자                 | 발주서·판매가·매입단가 승인이 SAP 안에만 있어 외부에서 결재 불가                 | 통합 결재함(건별 상세, 현재→변경단가 차이, 일괄 승인/반려+사유)           | 승인 대기 시간 단축                   |
| 배송기사               | 진행 상황을 전화로 문의받음                                                      | 모바일 웹에서 배송 목록 확인, 출발·도착·완료 버튼(위치 1회 수집)          | 문의 감소, 배송 완료 시점 기록        |
| SCM 담당자(VOC)        | 배송 문의에 건별로 SAP 조회·기사 통화                                            | 배송 현황 보드(라우트, 단계, 마지막 위치·시각), 고객용 조회 링크 발송     | VOC 대응 리소스 절감                  |

### 3.2 핵심 사용 시나리오

1.  **현장 발주 등록:** 영업사원 로그인 → 가맹점 검색 →
    헤더·매출요약·품목 입력 → 임시저장(오프라인 초안 포함) → 등록 → SAP
    발주서번호 회신 → 상신

2.  **외부 결재:** 결재자 알림 수신(Teams/메일) → 결재함 → 건 상세 확인
    → 승인/반려(사유 필수) → SAP 반영(Info Record 생성 결과 회신)

3.  **배송 조회:** 기사가 출발 버튼 → 위치·시각 기록 → SCM·고객은 현황
    보드/조회 링크로 확인 → 완료 버튼 시 SAP 배송상태 갱신

## 5. 개발 기획서

웹은 화면과 세션만 담당하고, 업무 판단과 권한의 최종 판정은 SAP(ABAP)에
둡니다. 웹이 뚫려도 SAP에서 한 번 더 막는 구조입니다.

### 5.1 기술 구성(안)

| 계층           | 구성                                                      | 비고                                                                  |
|----------------|-----------------------------------------------------------|-----------------------------------------------------------------------|
| 클라이언트     | 반응형 웹(PWA), React + TypeScript strict                 | 태블릿 우선, 모바일 대응. 앱 설치 불필요                              |
| 엣지           | WAF + CDN + TLS 1.2 이상                                  | AWS 사용 시 AWS WAF/CloudFront 등(인프라팀 확정 필요)                 |
| BFF(웹 백엔드) | Python FastAPI + MSAL Python, 타입 힌트 strict(mypy)      | 토큰은 서버 세션에만 보관, 브라우저에는 HttpOnly·Secure·SameSite 쿠키 |
| 웹 전용 DB     | 임시저장 초안, 감사 로그, 웹화면↔T-CODE 매핑, 배송 이벤트 | SAP 원본 데이터는 저장하지 않음(조회 시 실시간 호출)                  |
| 연동           | BSG AWS EAI (REST POST → SAP RFC)                         | 기존 화이트리스트+헤더 키 방식 → 상향 검토(6장)                       |
| SAP            | 신규 Z-RFC(원격 호출 가능 FM)                             | 기존 화면 로직을 FM으로 분리·재사용                                   |
| 비밀 관리      | 로컬 .env(개발용, .gitignore), 운영 Secrets Manager류     | 코드 내 하드코딩 금지                                                 |

### 5.2 로그인 흐름

1.  사용자가 .com 접속 → "Golfzon 계정으로 로그인" 단일 버튼

2.  OIDC Authorization Code Flow(+PKCE)로 Entra ID 호출 → 조직 도메인
    페더레이션에 따라 fs.golfzon.com 로그인 화면 표시

3.  조건부 접근 정책 평가(MFA 등) → 인가 코드 반환

4.  BFF가 토큰 교환·검증(발급자, 대상, 만료, 서명) → 사번/UPN 추출

5.  EAI를 통해 SAP 사용자 ID·역할·허용 화면 목록 조회 → 세션 생성 →
    대시보드

주의: fs.golfzon.com이 AD FS(온프레미스 페더레이션)인지, Entra ID
클라우드 인증인지 확인이 필요합니다. 어느 쪽이든 앱은 Entra ID에
등록하는 것을 전제로 합니다(9장).

### 5.3 권한 매핑 설계

| 단계          | 처리                                           | SAP 객체                                        |
|---------------|------------------------------------------------|-------------------------------------------------|
| ① 사용자 식별 | Entra 사번/이메일 → SAP 사용자 ID              | SU01 이메일(USR21→ADR6) 또는 별도 매핑 테이블   |
| ② 역할 조회   | 사용자에게 배정된 유효 역할(시작·종료일 포함)  | AGR_USERS, 복합 역할은 AGR_AGRS                 |
| ③ 화면 허용   | 역할의 T-CODE ∩ 웹화면 매핑표                  | AGR_TCODES(메뉴) + 웹 매핑 테이블               |
| ④ 실행 재확인 | 등록·승인 RFC 내부에서 해당 사용자 권한 재검사 | S_TCODE + 조직 권한 객체(예: 영업조직·구매조직) |

- 사실: AGR_TCODES는 역할 메뉴의 T-CODE 목록이며, 실제 실행 권한은 권한
  객체 S_TCODE(AGR_1251)로 판정됩니다. 파생 역할에서는 두 테이블 내용이
  다를 수 있다는 SAP KBA가 있습니다. ([SAP KBA
  3307728](https://userapps.support.sap.com/sap/support/knowledge/en/3307728))

- 따라서 메뉴 노출은 AGR_TCODES로 하되, **최종 차단은 ④ SAP 측 권한
  재검사**로 합니다. 조직 단위 제한(내 영업점 발주만)도 이 단계에서
  적용합니다.

- 승인·등록 이력의 처리자는 **RFC 기술 계정이 아닌 실제 사용자 ID**로
  남겨야 합니다(감사 추적성). 구현 방식은 ABAP팀과 확정합니다.

## 6. 보안성 검토 (보안팀 설득 자료)

**핵심 메시지:** 이 서비스는 VPN보다 접근 범위가 좁습니다. VPN은 사내망
전체에 네트워크 접근을 주지만, 본 서비스는 인증된 사용자에게 허용된 화면
몇 개만 열어 줍니다. 이는 네트워크 위치만으로 신뢰를 주지 않는
제로트러스트 원칙과 같은 방향입니다. ([NIST SP
800-207](https://csrc.nist.gov/pubs/sp/800/207/final))

### 6.1 접근 방식 비교

| 항목           | 현행 VPN + SAP GUI             | G-SAP Webservice                                         |
|----------------|--------------------------------|----------------------------------------------------------|
| 접근 범위      | 사내망(네트워크) 전체          | 허용 화면·API만                                          |
| SAP 노출       | SAP GUI가 SAP에 직접 연결      | SAP 비노출, EAI만 경유                                   |

  2022.6](https://www.kmcc.go.kr/download.do?fileSeq=53868))

  여부도 확인해야 합니다.

## 14. 발주서 입력 흐름 재설계

\[매출정보\]는 \[품목\]의 시스템별 합계이므로, v0.4는 품목을 먼저
입력하고 매출정보는 **한 화면 오른쪽 요약 패널에서 자동 합산**되게
바꿨습니다. 사람이 직접 넣는 것은 헤더, 품목,
결제조건(계약금·결제수단·여신사)뿐입니다.

<img src="media/image3.png" style="width:6in;height:2.77678in"
alt="발주서 입력 흐름 · 입력 3곳, 자동 계산 5곳" />

발주서 입력 흐름 · 입력 3곳, 자동 계산 5곳

- 데스크톱·태블릿 가로: 왼쪽 입력, 오른쪽 매출정보 요약(고정). 모바일:
  아래 고정 바에 총매출·잔금만 표시

- 품목이 없는 시스템(TV PLUS 등)은 '품목 없음'으로 흐리게 남겨 SAP
  화면의 5행 구조를 유지

- 확인 필요: 출하요청일자·납품시간이 시스템별로 다를 수 있는지, 헤더
  납품일을 기본값으로 써도 되는지 현업 확인

- 확인 필요: 최종금액 계산에 PM할인 외 '기타추가할인'(SAP 품목 컬럼)이
  어떻게 들어가는지 ABAP 로직 확인

## 16. 추가 제안

가장 먼저 권하는 것은 **화면 레지스트리**입니다. 웹 화면과 T-CODE의
연결을 코드가 아닌 데이터로 두면, 모듈 메뉴·MAIN 대시보드·즐겨찾기가
모두 같은 권한 기준을 따릅니다.

<img src="media/image4.png" style="width:6in;height:2.04464in"
alt="화면 레지스트리 · SAP 역할 → 메뉴·대시보드·즐겨찾기" />

화면 레지스트리 · SAP 역할 → 메뉴·대시보드·즐겨찾기

| \#  | 제안                           | 내용                                                                                   | 기대 효과(추정)                      |
|-----|--------------------------------|----------------------------------------------------------------------------------------|--------------------------------------|
| P1  | 화면 레지스트리                | T-CODE → 화면ID·모듈·하위모듈·웹 제공 상태를 관리자 화면에서 관리                      | 프로그램 추가 시 배포 없이 메뉴 반영 |
| P2  | 업무 레이어 + 모듈 레이어 병행 | 현장 사용자는 'SD'보다 '발주서'로 찾음. 홈 상단은 할 일·즐겨찾기, 아래는 모듈          | 외부 영업사원 학습 부담 감소         |
| P3  | Fiori Launchpad 구조 차용      | Space=모듈, Page=하위 모듈, Tile=프로그램으로 대응. 사내 Fiori 구성과 용어·구조를 맞춤 | 내·외부 화면 구조 통일               |
| P4  | MAIN 대시보드 + 즐겨찾기       | 역할별 지표·할 일 위젯, 허용 프로그램 중 즐겨찾기 고정(서버 저장)                      | 매일 쓰는 화면까지 1클릭             |

| P6  | 디자인 토큰 고정               | 스킬 1개를 정한 뒤 색·서체·간격을 토큰 파일로 확정, 이후 화면은 토큰만 사용            | AI가 만든 듯한 들쓰남 방지           |

  것과는 다릅니다. 외부 공개 방식 비교는 별도 검토가 필요합니다.
